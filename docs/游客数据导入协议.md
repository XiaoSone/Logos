# 游客数据导入与账号生命周期（2026-10-19）

这是 Phase 1 的开发账号同步实现。游客模式只写本机；用户在“账号与同步”页同意合并并连接开发账号后，游客数据归入该账号的本地库，开始上传与云端缓存拉取。正式短信、refreshToken、服务端会话撤销、PG16/Redis 及真机断网恢复验收仍未完成，不能作为生产账号体系发布。

## 本地数据库 v2

- `bookmarks`：收藏/高亮/备注及创建、更新时间；同节一条。
- `notes`：标题、正文、经文 ID 列表、标签、时间；列表使用 JSON 数组保存，标签中的逗号、引号保留原义。
- `reading_progress`：书卷、章、节、时间；同章节号取最大值。
- `feed_record`：沿用既有历史快照及游标，保留分享中的全部经文 ID。
- `settings`：保留阅读位置、设置和设备经文密文缓存；凭证及设备密钥继续使用安全存储。
- `sync_queue`：每个 `(kind, client_key)` 保存最新操作、UUID `revision`、完整载荷和入队时间。业务数据与队列、关联记录在同一事务中写入。

升级在事务中将 v1 `user_data` 迁入独立实体表，并重建全部存量游客数据与分享的待上传队列。v1 从未上传业务数据，因此重建不会重复已同步数据；迁移结束才删除旧表。未知或损坏的旧行导致整体回滚，不静默跳过。升级不改设置或个人记录，读取记录时仍按已有规则清理旧选中记录和失效高亮。

删除收藏/笔记后，实体行删除，队列保留 `DELETE` 与原自然键、删除时间。对某个队列快照确认成功时，只删除 `revision` 仍相同的行；请求期间的新编辑、删除或重新创建继续待上传。单纯准备批次不确认任何数据。

## GraphQL 接口

`importGuestData(items: [GuestDataItem!]!): ImportResult!` 只接受已验证的用户 token。userId 来自会话，输入不接受 userId 或 deviceId。游客及无凭证请求均拒绝，游客业务数据不会写入服务端。

每批 1–100 项，批内 `clientKey` 唯一、最长 36 字符。每项需要：

| 字段 | 语义 |
|---|---|
| `clientKey` | NOTE/FEED_RECORD 的本地稳定 ID；BOOKMARK/PROGRESS 使用实际自然键决定实体 |
| `revision` | 当前队列版本的 UUID；同一版本重试必须使用完全相同的输入 |
| `type` | BOOKMARK / NOTE / PROGRESS / FEED_RECORD |
| `operation` | UPSERT（默认）或 DELETE；当前 DELETE 仅支持收藏、笔记 |
| `createdAt` | 原始创建时间；偏离接收时钟超过 24 小时夹取为接收时间 |
| `updatedAt` | 冲突版本时间；允许历史离线时间，超前超过 24 小时夹取为接收时间 |
| `verseRefs` | 可校验的书卷章节引用；范围展开并去重后最多 100 个节地址 |

收藏必须引用单节，颜色为空或 `#RRGGBB`，备注不超过 2000 字符。笔记正文非空且不超过 50,000 UTF-8 字节，标题不超过 200 字符，标签不超过 20 个、每个不超过 30 字符，章节范围描述不超过 30 字符。进度必须是存在的书卷章节节号。分享上传 `recordType: SCRIPTURE_SHARED`、完整 `verseRefs` 和 `content` 快照。

与原 v1.1 蓝图的调整：增加 `revision`、`operation`、`updatedAt`，用于可靠重试、删除与 LWW；引用上限从 50 调到 100，以兼容已验收的笔记目录选择上限；显式 Feed 上传改为当前实际产品保留的分享记录。选中经文不再生成记录，收藏/笔记的记录由服务端自动生成，客户端不重复上传。创建时间沿用蓝图的 24 小时夹取；更新时间保留历史值，避免多日前的离线编辑被误当作最新版本。超过 24 小时的历史创建时间仍会按该规则调整，时间线恢复精度受此限制。

```graphql
mutation ImportGuestData($items: [GuestDataItem!]!) {
  importGuestData(items: $items) {
    imported
    failed
  }
}
```

`GuestImportBatch.items(referenceForId)` 从持久化队列快照生成上述变量，通过调用方提供的 ID→引用转换函数生成 `verseRefs`。转换失败不改队列。`AccountManager` 在用户连接开发账号后调度上传；引用从 APK 结构索引计算，不需要先解密经文正文。

## 事务、冲突与确认

- 同一用户的导入与收藏/笔记写操作以用户行锁串行化；不同用户独立。
- `guest_import_receipt` 保存 `(user_id, revision)` 和载荷 SHA-256。相同版本重试无重复业务行或 Feed；复用版本但换载荷返回失败项。回执保留至账户删除，不因删除某条笔记而删除。
- `guest_import_state` 保存用户、类型、自然键的更新时间及删除状态。收藏/笔记按更新时间 LWW，同时间删除优先；正常云端删除同样写入状态，旧版本不能通过重新插入绕过删除。
- 进度独立按最大节号、最大阅读时间合并，较早时间携带的更大节号也能合入。
- 笔记按 clientKey 更新正文、标签及关联经文；创建时才自动生成一条笔记记录。分享按 clientKey 幂等保存完整经文 ID 列表，`FeedRecord.verseIds` 返回完整列表，旧单节记录回退返回原 `verse_id`。
- 输入无效的项不写库，返回其 clientKey；其余合法项在一个事务中提交。数据库或其他非校验异常导致整个批次回滚，客户端不得确认队列。
- `imported` 是本批实际改变的实体数。重复版本或被较新数据覆盖的合法版本可能使其为 0；只要接口成功且 key 不在 `failed` 中，就可以确认该已提交版本。`GuestImportBatch.acknowledge` 仅确认成功项，并拒绝批次以外的失败 key。

这两个服务端辅助表通过 `schema.sql` 幂等创建，随账户外键级联清理。数据库升级后，v1 客户端不支持直接打开 v2；真机升级/回退验收需要保留匹配的私有数据库备份，单独保留旧 APK 不能回退已迁移的数据。PG16、真实账号生命周期、长时间多端冲突及真机数据库升级仍需后续验收。

## 账号隔离与游客归属

- 设备设置和经文缓存继续保存在既有 `guest.db` 的 settings 中。游客业务数据只在未连接账号时写入该库。
- 账号业务库为 `user_<规范服务地址的 SHA-256>_<userId>.db`；Web 使用同样命名的独立 IndexedDB。服务地址和经验证的用户 ID 共同决定缓存归属，deviceId 不参与用户身份判断。
- 同时只使用一份活动业务库。切换期间阻止新写入，等待已开始的本地操作完成，再关闭旧账号库。切换后重新加载笔记、收藏、分享、进度、最近位置和搜索历史。旧账号草稿保存前再次检查原库，旧请求返回时检查账号上下文，均不能写入新账号。
- 账号凭证连同绑定的服务地址、用户 ID 和脱敏手机号作为一条 JSON 写入 flutter_secure_storage；不进入 SQLite、导出备份或日志。客户端不提供生产 refreshToken，当前一小时开发 token 过期后需重新连接同一账号；缓存和队列仍可离线使用。
- 登录状态下修改服务地址会被拒绝；退出后可以切换地址，原服务的账号缓存仍隔离保留。不会将旧服务凭证发送到新地址。

游客转移使用可恢复的两步提交：先在游客 settings 写入包含服务地址、userId、transferId 的 `guestTransfer` 归属标记，目标账号在事务中合入实体、删除队列、完整分享与个人位置/历史，并记录 transferId；目标提交成功后才在游客库事务中清空业务数据与标记。已转移的队列尽量保留原 revision 和载荷，进度合并产生不同载荷时建立新版本。

任意一步中断，启动时优先恢复原归属标记。目标已提交时通过 transferId 跳过重复复制；未完成时游客数据被隔离，不能被其他账号接走，也不展示给新的游客。目标数据已提交但安全存储写入失败时，内容仍在原账号本地库，重新连接原账号可继续处理。空游客库连接其他账号不会复制上一个账号的数据。

退出会移除本机账号凭证、等待本地写入结束并关闭账号库，然后清空游客业务行及其个人位置/搜索历史。账号缓存与未上传队列保留在该账号的文件中；经文离线密文、设备密钥、服务地址和显示设置保留。这里采用“清空游客业务表并保留设备设置”，替代蓝图的整个 guest.db 删除，避免连带删除已下载的设备经文包。退出当前设备尚不撤销服务端已签发 token。

## 上传与云端缓存

连接账号、恢复登录后、应用回到前台、个人数据写入后和手动“立即同步”都会触发同步；写入触发有 400ms 去抖，同一时刻只进行一轮同步。失败或仍有待上传项时每 30 秒重试。没有未完成项时不持续轮询其他设备的变化，可通过前台恢复或手动同步拉取。

每轮先通过 `me` 验证 token 与预期 userId，再分批提交队列并逐版本确认。失败项留在队列，本轮后续批次会跳过已尝试的版本，避免某个错误项挡住其他数据。网络响应丢失时保留相同 revision 重试。退出或切换发生后，旧请求可能已在原账号云端提交，但其返回不会再确认本地队列或更新新账号；重连原账号后通过回执安全重试。

`mySyncSnapshot` 仅用户凭证可访问，返回 userId、全部收藏、笔记、进度与分享；在 PG REPEATABLE READ 只读事务中生成一致快照。笔记 `clientKey` 为稳定本地 ID，既有云端笔记在 schema 初始化时回填 UUID，后续创建也生成 UUID，客户端可通过该 key 编辑而不另建一篇。分享包括完整 verseIds，旧单节记录回退到 verse_id，不受原 Feed 默认 50 条分页截断。

完整响应到达后，客户端在单一 SQLite 事务中替换已同步缓存，并叠加当时尚未确认的本地新增、修改、删除与分享。拉取期间的新编辑不会被旧响应覆盖，服务端已删除的同步缓存行会移除；事务失败保留整份原缓存。拉取不会重新建立上传队列。新设备缺少最近位置时，从合并后的最近进度初始化“继续阅读”。页面的待上传数量、上次检查时间、失败说明与手动同步入口会按实际结果更新。

当前快照一次返回全部个人数据，适用于小范围开发账号；大规模分页同步、后台系统任务、实时多端通知和生产会话治理仍不在本批范围。
