# Logos 实施记录

输入：`wdbible_website_7_6_1.apk`、`Logos-技术架构方案.md` v1.1、https://github.com/morluto/rea。

## 工作顺序

1. 固定 APK SHA-256；静态清单、资源、DEX、依赖、网络协议与数据库证据分析。
2. 阅读 REA 的 Android/JADX 工作流，运行可用的分析链路并保存原始证据。
3. 建立功能对照矩阵，区分直接观察、静态推导、未验证行为。
4. 按架构方案创建 Flutter Android 客户端、Spring Boot 3 / Java 21 / GraphQL 后端、PG / Redis 开发环境。
5. 使用独立公共领域圣经数据；实现读经、目录、引用与关键词搜索、每日经文、本地收藏/高亮/笔记/记录、阅读进度、设置。
6. 构建、自动测试、视觉检查与交付；列出尚未达到架构验收要求的部分。

## 范围解释

“复刻”以架构方案 1.2.1、8 章定义的核心体验为准。原 App 的社交、群组计划、付费内容作为分析范围，不作为 Logos 第一阶段实现范围。AI 问答、知识图谱按文档留在后续阶段。

所有重实现代码独立编写；APK 提取物仅用于分析证据，不进入产品资源包。

## 已落地的项目结构

- Flutter 客户端实现游客读经闭环：目录、章节、引用和字面搜索、高亮、收藏、笔记、记录流、历史、设置及设备加密离线缓存。
- Spring Boot 单服务提供 GraphQL 目录、搜索、每日经文、凭证/密钥和个人数据 API；已建立 15 张基础表，用户身份由签名凭证注入。
- 导入器固定公共领域 USFM 快照及哈希，生成服务端数据、客户端结构索引和 AES-GCM 密文。诗篇题注与雅歌发言人保存在段标题，合节保留源范围。
- 本地开发 PG 与机器上其他数据库隔离，端口 55432。Compose 指向目标 PG16 / Redis7；本次实际集成使用 PG18。
- 原 App 安装后未能跨过 ARM JNI 初始化；报告因此保留运行行为、完整后端协议、Native 算法和精确视觉还原的未知项。

## 构建过程中的修复

1. Kotlin 插件的 C 盘 Pub 缓存与 D 盘项目跨盘增量缓存失败，已关闭 Kotlin 增量编译。
2. 构建、分析器与模拟器同时运行造成内存耗尽，改为串行构建和预构建测试 APK 后运行。
3. API30 软件 GPU 的 Impeller shader 超出 uniform 限制；最新源码已配置 Skia，当前成功 APK 尚未包含该修改，设备图形/性能仍待验收。
4. Web 的大容量离线密文改用 IndexedDB 持久化，避免依赖小容量 localStorage 保存 SQLite 数据。
5. 视觉验收发现诗篇题注混入第一节，已修正 USFM d/sp 处理并添加诗篇 46:1 回归断言。

最终结果以《验收记录》为准。后续优先完成类型化本地表、游客合并和账号同步，再接正式认证与生产治理；不要先进入 AI 阶段。
